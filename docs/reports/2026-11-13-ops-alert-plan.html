감시 개선 계획

2026-11-13 작성, 같은 날 확인, 상황실, 조치 세 부서 구조로 고침. 리포 Deepbluewarn/twitch-badge-collector-v2, 작업 위치 ~/development/twitch-badge-collector-v2. 다른 세션이 이어서 작업할 수 있게 근거와 파일 위치를 같이 적었다. 같은 날 앞서 쓴 "감시 알림 정리 계획"(알림 기록, GitHub 이슈, 스킬)을 대신한다.

목표는 두 가지다.
  1. 신호를 믿을 수 있게: 울리면 진짜 문제이고(오탐 없음), 사용자에게 문제가 생기면 울린다(놓침 없음).
  2. 빨리 고칠 수 있게: 치지직 배포에서 사용자에게 고친 선택자가 닿을 때까지의 시간을 줄인다.

전수 조사 결과, 지금 체계는 잘 돌지만(11일 동안 실패 4번) 놓치는 곳이 구조적으로 있다. 11-12 치지직 배포 때 선택자 카나리는 "정상"이었다. 그리고 확인하는 작업들이 알림까지 각자 보내서 규칙이 7가지다.

그래서 일을 세 부서로 나눈다. 확인부는 결과만 남기고, 상황실 하나가 판정, 기록, 알림을 맡고, 조치부는 되돌릴 수 있는 일만 자동으로 하고 나머지는 사람이 한다.

확인부치지직, 확장, 사용자, 감시 작업을 보고 정해진 양식으로 결과만 남긴다. 알림을 직접 보내지 않는다.
→결과 파일
상황실모든 결과를 모아 사건을 가리고(새로 생김, 이어짐, 회복), 긴급과 참고로 나눠 보내고, 전부 기록한다. 직접 고치지 않는다.
→알림, 이슈
조치부다시 확인, 캐시 비우기, 반영 확인은 자동. OTA 푸시, 단계 배포 멈춤, 릴리스는 사람.

두 부서(확인, 조치)가 아니라 세 부서인 이유: "진짜 문제인가, 얼마나 급한가"를 정하는 규칙이 한 곳에 모여야 신호를 믿을 수 있다. 조치에는 자동으로 해도 되는 것과 사람이 해야 하는 것이 섞여 있어 판정과 따로 둔다.

1) 결과 양식 (확인부 → 상황실)

interface CheckResult {
  check: string;          // 'deploy' | 'selector' | 'vod' | 'socket' | 'live' | 'bundle' | 'usage' | 'heartbeat' | 'badges' | 'spike'
  at: number;
  status: 'ok' | 'issue' | 'unknown' | 'error';   // 정상, 이상, 확인 못 함, 실행 실패
  findings: Finding[];    // issue일 때 이상마다 하나
  note?: string;          // unknown, error일 때 이유 (예: "방송 채팅 없음", "zip 504")
}
interface Finding {
  key: string;            // 같은 문제는 같은 key. 예 'selector:badge:branch1', 'live:치지직 소켓 끔:no-badge', 'badge:<imageUrl>'
  level: 'broken' | 'risk' | 'info';
  title: string;          // 알림 첫 줄
  lines: string[];
  evidence?: unknown;     // 수정 후보, 배지 JSON 한 줄, 문제 목록 등 (이슈 본문과 S1에 그대로 씀)
}

  • 확인부 작업에서 sendDiscord 호출을 모두 뺀다: deploy.ts, canary.ts, new-badges.ts, heartbeat.ts, spike-alert.ts, render.ts. 선택자 카나리 스크립트의 직접 알림은 ops/watch/canary.ts selector SPEC env에 DISCORD_CANARY_WEBHOOK: ''를 넣어 끊는다(소켓은 이미 이렇게 한다). chzzk.ts의 canary-alert.json은 findings의 재료로 쓴다.

T6. 주 경로 시험: 수집 창이 생기는지, 소켓 경로가 살아 있는지 가장 중요

왜: 치지직 라이브는 소켓 경로가 100% 켜져 있고(socketRenderPercent: 100), 선택자는 대체 경로다. 그런데 지금 감시는 대체 경로를 가장 촘촘히 본다. 가장 큰 고장은 두 가지다.

  • 수집 창이 아예 안 생김: 창은 소켓이든 HTML이든 채팅 컨테이너 선택자(chatRoomLive)에 붙는다. 지금은 6시간 주기 시험만 이걸 보고, 창이 없는 것과 비어 있는 것을 구분하지 않는다. 방송 쪽 채팅 수를 고정 선택자로 세서 치지직 화면이 바뀌면 "확인 못 함"이 되고, 위험이 되기까지 18시간이 걸린다.
  • 소켓 경로가 조용히 죽음: 확장의 탭(ws-tap.ts)은 페이지가 wss://*.chat.naver.com/chat을 메인 스레드에서 열 때만 붙는다. 주소가 바뀌거나 소켓이 다른 곳으로 옮겨지면 탭은 아무것도 못 받고 확장은 HTML 경로로 넘어간다. 사용자도 감시도 모른다. 소켓 카나리는 자기 연결로 패킷 모양만 봐서 이걸 못 잡는다.

무엇을: 1시간마다 확장을 올린 Chromium으로 치지직 인기 라이브 하나를 소켓 모드로 60초 본다(ops/watch/live-check.ts --main). 확장 코드는 바꾸지 않는다.

  • 방송 채팅은 소켓으로 센다: Playwright로 페이지의 웹소켓 메시지를 받아 채팅 명령 수를 센다. 화면 구조에 기대지 않으니 치지직 화면이 바뀌어도 "확인 못 함"으로 빠지지 않는다.
  • 창이 생겼나: 수집 창 요소가 없으면 깨짐(main:no-pane). 채팅 컨테이너 선택자가 맞는지 같이 적는다.
  • 창에 채팅이 들어오나: 창은 있는데 비면 깨짐(main:empty-pane).
  • 소켓 경로: 탭이 기다리는 주소의 소켓이 열렸는지, 그 메시지를 확장의 파서(parseChzzkPacket)가 채팅으로 읽는지 본다. 채팅은 오는데 탭 주소의 소켓이 없거나 파서가 못 읽으면 위험(main:socket-path, "HTML 대체로 동작 중"). 창까지 비면 위 깨짐이 같이 뜬다.
  • 6시간 실제 시험(소켓 끔, 트위치, 번들 검사)은 그대로 두고, 창 유무 구분과 소켓으로 센 방송 채팅 수를 거기에도 넣는다.

T2. 확장 실제 시험의 보고를 바로잡기 중간

왜: 가장 강한 신호인데 오탐 두 번, 배지가 빠지는 고장은 못 잡는다.

  • 확인 못 함을 따로 (ops/watch/live-check.ts):
    • zip 다운로드는 3번까지 다시 받는다. 같은 버전 zip이 캐시에 있으면 그걸 쓴다. 그래도 실패하면 unknown(note "zip 받기 실패")로 남긴다.
    • 방송 쪽 채팅이 10줄 미만이면 다음 순위 방송으로 한 번 더 한다(치지직 인기 목록 5위, 7위, 트위치 목록 5위, 7위). 그래도 모자라면 그 경로는 unknown. 오래 이어질 때 위험으로 올리는 일은 상황실 규칙(R1)이 한다.
  • 놓침 제거:
    • 수집 창 줄 수가 방송 줄 수의 30% 미만이면 risk. 치지직에서 방송 쪽에 배지가 있는 채팅이 있는데 수집 창의 배지 붙은 줄이 0이면 broken. 닉네임이 빈 줄이 절반을 넘으면 broken. 방송 쪽 배지 줄 수를 같이 센다.
    • 필터를 하나 더 넣는다: 방송에서 실제로 보인 배지 하나로 배지 필터를 만들어, 그 배지 단 채팅이 수집 창에 오는지 본다. 사용자가 가장 많이 쓰는 경로다. 배지 필터 하나만 확인하는 간단한 시험이다.
    • 전체 채팅을 잡는 필터: 지금의 빈 키워드 대신 "닉네임이 \u0000이 아님" 조건을 쓴다. 모든 채팅이 수집 창에 와야 하므로 아래 비교의 기준이 된다.
    • 메시지 종류별 짝 비교: 방송 화면과 수집 창의 같은 채팅을 짝지어, 일반 채팅, 후원, 구독 같은 메시지 종류마다 닉네임, 본문, 배지가 맞게 나오는지 본다. 선택자가 맞아도 수집 창에서 잘못 그려지는 고장을 잡는다.
    • 배지 묶음별 비교: 방송 화면의 배지와 수집 창의 배지를 묶음(역할, 순위, 후원, 구독, 치트키, 리캡, 팝업, 업적, 인증 마크)마다 센다. 방송 쪽에 그 묶음이 없으면 그 묶음은 unknown이다.
  • 소켓 경로: 소켓 카나리가 배지를 만드는 네 출처(profile.badge, realTimeDonationRanking, subscription, viewerBadges/activityBadges)가 패킷에 계속 있는지 센다.
  • 버전 맞추기: 스토어 공개 페이지 버전(info.ts가 이미 받는다)과 최신 릴리스가 다르면 실행마다 번갈아 시험하고 결과에 버전을 적는다. 단계 배포 중 두 버전 모두 사용자에게 있기 때문이다.

T3. 실제 사용자 수집 비율 확인 중간

왜: 카나리는 방송 몇 개를 보지만 이건 하루 8천 명의 채널, 필터, 브라우저를 본다. 카나리가 놓친 고장을 잡는 그물이다.

  • findings (치지직만, 표본 500명 이상인 칸만):
    • 어제 비율이 지난 7일 중앙값보다 8%p 넘게 낮으면 risk, 20%p 넘게 낮으면 broken. 기준 숫자는 2주 기록을 더 보고 정한다(지금 7일 범위가 79~86%).
    • 같은 날 버전끼리: 새 버전 비율이 옛 버전보다 5%p 넘게 낮으면 risk (S3과 이어짐).

9. 작업: 조치부

S1. 알림 한 번으로 고칠 수 있게 중간

왜: 조치 7시간의 상당 부분은 알림을 받은 뒤 다시 조사하는 시간이다. 증거와 고칠 내용이 알림 안에 있으면 확인, 적용, 푸시만 남는다.

  • 알림 내용 (확인부의 evidence를 상황실이 그대로 싣는다): 무엇이 깨졌나(선택자 이름, 갈래), 영향(어느 기능, 실제 시험과 사용자 비율 결과), 검증된 수정 후보, 절차 문서. 선택자 깨짐과 갈래 죽음(T1)은 rev를 올린 bundled-selectors.prod.json, bundled-selectors.json 바뀔 줄을 그대로 붙인다.
  • GitHub 이슈 (상황실이 연다): 긴급 사건 중 고칠 대상(selector, vod, socket broken, live broken, usage 하락)만. 같은 key가 열려 있으면 댓글, 회복이면 댓글 달고 닫는다. 본문 끝에 <!-- ops-alert key: ... -->를 남겨 incidents.json이 사라져도 찾을 수 있게 한다. 라벨 ops-alert, ops:<check>. 토큰은 ovm ops.env의 GITHUB_ISSUES_TOKEN(Issues 쓰기만). 없으면 이슈 단계만 건너뛴다. 예전 git show d0a50df^:scripts/canary/open-alert-issue.mjs를 참고한다.

  • 이슈 열림, 닫힘 시각이 1장의 조치 시간이 된다. "확장 문제 아님"으로 닫은 이슈가 오탐률이 된다.

S2. OTA 도달을 15분 안으로, 그리고 확인 작음

왜: 고쳐 푸시해도 jsDelivr가 최대 12시간 옛 파일을 낸다. 지금은 손으로 purge하고, 확인하는 감시가 없다.

  • .github/workflows/site-rebuild.yml처럼 src/platform/bundled-selectors*.json이 바뀌면 jsDelivr purge하는 워크플로(또는 같은 파일에 job 추가). 워크플로 파일은 SSH로 푸시한다(규칙 참고).
  • ovm pull 작업: 이번 pull에서 선택자 파일이 바뀌었으면 jsDelivr가 그 rev를 낼 때까지 1분 간격으로 확인하고(최대 30분), 그 뒤 canary와 live를 띄운다. live는 확장이 jsDelivr에서 OTA를 받으므로 사용자와 같은 길로 고친 결과를 확인한다.
  • 결과는 확인부 양식으로 watch/checks/ota.json에 남긴다: 도달하면 info "rev 22 도달", 30분 지나도 안 보이면 risk. 실제 시험 결과는 live 사건의 회복으로 이어진다.

S3. 단계 배포를 멈출 근거 중간

왜: scheduled-publish.yml이 매일 10 → 50 → 100%로 올린다. 새 버전 고장은 10%일 때 막으면 사용자 90%가 피한다. 지금은 멈출 근거가 없다.

  • 1단계: T3의 버전 비교가 risk면 상황실이 긴급 알림에 "단계 배포 멈추기: gh workflow disable scheduled-publish.yml"을 같이 보낸다. 사람이 멈춘다.
  • 2단계(1단계로 몇 번 써 본 뒤): 워크플로가 단계를 올리기 전에 ovm 판정을 읽는다. 방법은 둘 중 하나. (a) 워크플로가 Cloudflare 읽기 토큰으로 직접 쿼리, (b) ovm이 판정을 GitHub 릴리스의 표시 파일이나 커밋 상태로 올림. 데이터가 하루 늦어 10% 단계를 하루 더 두는 것도 같이 정한다.

11. 하지 않는 것

  • Claude를 사람 없이 돌려 고치기(ovm에서 claude -p, 클라우드 루틴, GitHub Actions용 Claude). 구독 계정 약관 문제로 사용자가 뺐다. 고치는 일은 사용자가 연 세션에서 한다.
  • OTA 자동 푸시. master 푸시가 곧 사용자 배포다. 예전 무단 OTA 배포 사고가 있었다. 사람 확인은 남긴다.
  • 확장에 새 진단 신호 넣기(예: 수집 창이 몇 분째 비면 즉시 보내는 통계). 하루 늦은 문제를 풀지만 확장 릴리스, 처리방침 변경이 필요하고 "있는 듯 없는 듯" 원칙과 부딪힌다. T3을 써 본 뒤 다시 본다.
  • 트위치 사용자 비율 판정. 하루 40~60명으로는 안 된다.
  • 커뮤니티 감시를 상황실로 옮기기. 리포 밖이고 보고라 그대로 둔다.
  • 급증, 새 배지 감시 자체 손보기. 설계대로 돈다. 알림 길만 상황실로 옮긴다.

13. 지켜야 할 규칙

  • 답변은 한국어. 코드 주석과 커밋 메시지도 한국어(기존 스타일).
  • 엠대시, 가운뎃점 문자 금지. 답변, 커밋, 주석, 알림 문구, 문서 전부.
  • 소프트웨어 의인화 금지. 코드, 주석, 알림 문구, docs/monitoring.md에서 "알려 준다", "판단한다" 대신 "표시한다", "판정한다". 이 문서의 직원 명부는 사용자가 요청한 비유라 예외다. 부서 이름(확인부, 상황실, 조치부)도 코드와 운영 문서에는 쓰지 않고 check, dispatch로 쓴다.
  • 파일을 지정해서 스테이징. git add -A, git add . 금지. 여러 세션이 작업 트리를 같이 쓴다.
  • master에 바로 커밋, 푸시. 브랜치, worktree, PR 없음. ovm은 10분마다 master를 받으므로 푸시가 곧 ovm 배포다.
  • ops를 고치면 docs/monitoring.md 변경 이력에 한 줄. crontab, systemd를 고치면 ovm에서 직접 설치(docs/monitoring.md "고치는 법").
  • ovm에서 시험: ssh ovm 'cd ~/tbc && git pull -q && npx tsx ops/watch/<파일>.ts --dry-run'. 브라우저 작업(canary, live, vod)은 잠금을 같이 쓴다. 메모리 7GB.
  • 워크플로 파일은 SSH로 푸시(gh 토큰에 workflow 권한 없음). S2에 해당.
  • 선택자 JSON(bundled-selectors*.json)은 시험으로라도 rev를 올려 푸시하지 않는다. 곧바로 사용자에게 나간다.
  • 확장 코드를 고쳐 릴리스하게 되면 CLAUDE.md의 "릴리스 전 실제 업데이트 시험"을 거친다. 이 계획의 작업은 모두 ops, 카나리 스크립트, 워크플로만 바꾼다.
  • 보고서는 리포 안 파일로. Claude 아티팩트, /tmp 금지.

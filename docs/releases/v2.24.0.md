# v2.24.0

v2.23.0 이후 변경 사항. 확장이 업데이트될 때 수집이 멈추고, 새로고침하면 모아 둔 채팅이 사라지던 문제를 고쳤다. 배포는 새벽 4시 단계적 배포로 바꿨다.

## 1. 릴리스 노트

GitHub Release 본문과 스토어 "이번 버전의 새로운 기능"에 그대로 붙여 넣는다.

```
v2.24.0

- 확장 프로그램이 업데이트되면 채팅 수집이 멈추던 문제 수정
```

## 2. 달라진 점 안내

### 업데이트돼도 수집이 이어진다

지금까지 Chrome에서는 확장이 업데이트되면 이미 열려 있던 방송 탭의 수집이 조용히 멈췄다. 새로고침해야 다시 모였고, 그때 모아 둔 채팅도 사라졌다. Firefox는 업데이트 때 열린 탭에 새 코드를 스스로 넣어 줘서 이 문제가 없었다.

이번 버전부터는 Chrome에서도 업데이트 직후 열린 탭에 새 코드를 넣는다. 사용자는 아무것도 하지 않아도 된다.

- 모아보기 창은 하나만 보이고, 수집이 바로 이어진다.
- 업데이트 전에 모아보기 창에 있던 채팅은 그대로 남는다. 채팅 유지 설정과 상관없다.
- 2.23.0에서 이번 버전으로 올라올 때도 마찬가지다.

### 채팅 유지가 업데이트에도 남는다

채팅 유지(새로고침, 탭 이동 후에도 수집 내용 유지)의 저장 위치를 바꿨다. 예전 위치는 확장이 업데이트될 때 비워졌다.

- 업데이트 후 새로고침해도 채팅이 남는다.
- 브라우저를 껐다 켜면 지워지는 것은 예전과 같다.
- 최근 방송 20개까지만 저장하고, 전체 용량도 묶어 두어 필터와 설정을 저장할 공간을 남긴다.

## 3. 개발 변경 사항

### 권한

| 권한 | 용도 | 설치, 업데이트 경고 |
|---|---|---|
| `scripting` | 업데이트 직후 열린 치지직, 트위치 탭에 패키지 안의 콘텐츠 스크립트를 다시 실행 | 없음 (기존 호스트 권한 범위 안) |

Chrome 웹 스토어 개인정보 탭의 사용 이유:

```
확장 프로그램이 업데이트된 직후, 이미 열려 있는 치지직, 트위치 탭에 확장 프로그램 패키지에 포함된 콘텐츠 스크립트를 다시 실행합니다. 사용자가 페이지를 새로고침하지 않아도 채팅 모아보기가 계속 동작하게 하기 위해서이며, 원격 코드는 실행하지 않습니다.
```

### 업데이트 처리 흐름

1. 새 background가 `onInstalled`(reason `update`)에서 열린 탭에 `scripting.insertCSS`, `executeScript`로 콘텐츠 스크립트를 넣는다. 평소 콘텐츠 스크립트가 들어가는 프레임만 고른다(`webNavigation.getAllFrames` + match pattern). Firefox는 스스로 넣으므로 하지 않는다. MAIN world 스크립트는 페이지에 살아 있어 다시 넣지 않는다.
2. 새 콘텐츠 스크립트는 시작하자마자 옛 모아보기 창의 채팅을 떠 둔다(`salvage.ts`). 그다음 `tbcv2-instance` 이벤트를 보내 옛 스크립트를 물러나게 하고, 남은 옛 창은 숨기고 id에 `-stale`을 붙인다. 지우지 않는 이유는 2.23.0 팝오버 창에 "떼어지면 다시 붙이는" 감시가 있어서다.
3. 새 모아보기 창은 처음 채울 때 떠 둔 채팅부터 넣고, 저장소에 더 오래된 채팅이 있으면 이어 붙인다.
4. 옛 스크립트는 2초마다 `runtime.id`로 끊김을 본다. 끊겨도 6초는 새 스크립트를 기다린다. Chrome이 탭을 하나씩 돌며 넣어 뒤쪽 탭이 늦기 때문이다. 그 안에 새 스크립트가 없으면 등록된 정리를 돌리고 안내를 띄운다.

### 주요 파일

- `src/content-scripts/base/lifecycle.ts`: 인스턴스 교대, 끊김 감지, 정리 등록(`onTeardown`), 안내
- `src/content-scripts/base/salvage.ts`: 옛 창 채팅 떠 두기, 넘기기
- `src/content-scripts/base/container.tsx`: `restoreHost`(원본 채팅 목록의 id, 높이, 순서 되돌리기)
- `src/utils/chat-history-store.ts`: 채팅 유지 저장소. storage.session에서 storage.local로. 브라우저 시작 때 삭제(background `onStartup`), 채널 20개, 채널당 1MB, 전체 4MB
- `src/hooks/useFilteredChatBuffer.tsx`: 저장 간격 2초(throttle), 옛 창 채팅으로 처음 채우기
- `src/entrypoints/background.ts`: `reinjectContentScripts`

### 배포 자동화

릴리스를 Publish하면 바로 내보내지 않고 새벽 4시(한국 시간)에 내보낸다.

| 시점 | Chrome | Firefox | Edge |
|---|---|---|---|
| 릴리스 Publish | 심사 제출(`STAGED_PUBLISH`, 승인돼도 대기). zip을 릴리스에 첨부 | 없음 | 심사 제출(승인 즉시 게시) |
| 첫 새벽 4시 | 승인돼 대기 중이면 10% 게시 | 첨부된 zip으로 제출 | 없음 |
| 다음 날 새벽 4시 | 50% | 없음 | 없음 |
| 그다음 날 새벽 4시 | 100% | 없음 | 없음 |

- 파일: `.github/workflows/publish.yml`, `.github/workflows/scheduled-publish.yml`, `scripts/cws.mjs`
- Chrome Web Store API v2 사용(v1.1은 2026-10-15 종료 예고). 시크릿 `CHROME_PUBLISHER_ID` 추가
- 단계적 배포는 7일 활성 사용자 1만 명 이상만 된다. 거절(4xx)되면 100%로 게시한다
- 문제가 보이면 Scheduled Publish 워크플로를 끄면 비율이 더 올라가지 않는다. 비율은 내릴 수 없다
- 디스코드 공지는 Chrome이 실제로 게시된 날 한 번
- 제출, 공지 여부는 릴리스에 붙이는 표시 파일(`firefox-submitted.txt`, `notified.txt`)로 기억한다
